Universal, Model-Agnostic Context Caching Harness

To build a cache harness that works across all models—including proprietary APIs (Gemini, Anthropic, OpenAI) and self-hosted models (vLLM, SGLang, Ollama, llama.cpp)—you must understand how cross-model caching works:

    1. How Local Models Cache: Inference engines like vLLM and SGLang use Automatic Prefix Caching (RadixAttention). They match the tokenized Key-Value (KV) cache of the initial tokens of a prompt across different requests. If two prompts share the exact same starting prefix, the engine reads the precomputed KV values directly from GPU memory at near-zero compute latency.

    2. How Cloud APIs Cache: Providers like Anthropic, OpenAI, and Gemini also cache strictly from the first token forward (prefix matching).

If your prompt changes dynamic tokens near the beginning, the entire cache breaks across every engine.

Step 1: Enforce Strict "Static-Prefix" Prompt Topology
Order every prompt strictly from most static to most dynamic:

┌────────────────────────────────────────────────────────┐
│  Tier 1: Static System Directives & Architecture Specs │  <- 100% Shared (Always Cached)
├────────────────────────────────────────────────────────┤
│  Tier 2: Static JSON Schemas & Guardrail Rules         │  <- 100% Shared (Always Cached)
├────────────────────────────────────────────────────────┤
│  Tier 3: Few-Shot Static Demonstrations                │  <- 100% Shared (Always Cached)
├────────────────────────────────────────────────────────┤
│  Tier 4: Dynamic Agent Card & Context (Payload)        │  <- Dynamic per Request
├────────────────────────────────────────────────────────┤
│  Tier 5: Dynamic Critic Feedback / Corrections         │  <- Only present during retries
└────────────────────────────────────────────────────────┘



Enabling Prefix Caching on Local Engines

When deploying local models to serve as your LLM provider, pass the prefix caching flag during engine startup so the static system prefix is kept warm in the GPU's memory:

    vLLM: "vllm serve mistralai/Mistral-Large-Instruct-2407 --enable-prefix-caching"

    SGLang: "python3 -m sglang.launch_server --model-path mistralai/Mistral-Large-Instruct-2407"
    # (RadixAttention prefix caching is enabled by default in SGLang)

    llama.cpp / llama-server: "./llama-server -m model.gguf --prompt-cache system_prefix.bin --cache-ram 4096"

With the prompt harness ensuring the prefix bytes are 100% identical on every execution, both local inference engines (via KV cache reuse) and commercial cloud APIs will run at maximum throughput and minimal token cost.












To build a universal, reusable Python package that optimizes token costs across any agent workflow, the caching strategy must operate on two distinct levels simultaneously.

1. The Dual-Layer Caching Architecture:
    Level 1 (L1) - Application Exact Cache: This layer intercepts identical LLM requests before they are sent over the network, returning a stored output for zero compute cost. Because different dictionary key ordering produces different cache hashes, this layer relies on deterministic serialization (using sort_keys=True in json.dumps()) to ensure consistent cache hits.

    Level 2 (L2) - Engine Prefix Cache: When an L1 miss occurs, the package must structure the prompt to maximize Key-Value (KV) cache reuse inside the inference engine. This targets frameworks like SGLang, which utilizes RadixAttention to match token-level prefixes, and vLLM, which hashes fixed-size token blocks. Because a single whitespace difference can invalidate the entire cached prefix at the engine level, this layer strictly isolates static content at the top of the prompt and pushes dynamic variables to the very end.

2. Package Directory Structure
Create a dedicated package named agent_cache_harness in your project root. You can import this into Phase 2, Phase 3, or any external LangGraph workflow.

agent_cache_harness/
├── __init__.py
├── harness.py      # The main orchestrator class
├── builder.py      # Strict prefix-preserving prompt formatter (L2)
└── store.py        # Deterministic hashing and disk/redis storage (L1)











The dual-layer caching strategy operates on a simple principle: never pay an AI to think about the same problem twice, and never pay it to read the same instructions twice.

Here is the step-by-step breakdown of exactly how this system processes an incoming task.

    Step 1: The Request is Fingerprinted
    When your agent factory needs a new blueprint, it gathers the specific task details (the Agent Card). Before talking to the AI, the caching harness takes this specific data and creates a unique cryptographic fingerprint (a SHA-256 hash). Even a single changed comma will generate a completely different fingerprint.

    Step 2: Layer 1 (The "Skip the AI" Cache)
    The system checks your storage database (either your local hard drive or the Redis server) to see if this exact fingerprint already exists.

        If there is a match (Cache Hit): The system instantly pulls the saved blueprint from the database and returns it. The AI is completely bypassed. You pay zero tokens and experience zero processing delay.

        If there is no match (Cache Miss): The system must generate a new blueprint, which triggers the next layer of the strategy.

    Step 3: Formatting for Layer 2 (The Prefix Builder)
    Because the system must now talk to the AI, it needs to assemble the prompt. AI models process text sequentially from top to bottom. To optimize costs, the harness builds the prompt in a very strict order:

        The Top (Static Prefix): It places all the heavy, unchanging rules here—your extensive SEL guidelines, coding standards, and agent architecture rules. This section is identical every single time the factory runs.

        The Bottom (Dynamic Payload): It places the specific Agent Card and any error feedback at the very end of the prompt.

    Step 4: Layer 2 (The "AI Memory" Cache)
    The system sends this carefully structured prompt to the AI provider (like Google's Gemini API, or your local vLLM/SGLang server).

    When the AI engine receives the prompt, it checks its own internal memory (called a KV Cache). It recognizes that it has already read and processed the massive "Top" section from previous requests. Instead of reading and calculating those thousands of words again, it instantly loads its saved understanding of those rules from its GPU memory.

    The AI only spends time and processing power reading the "Bottom" section. You are only billed for the new tokens at the end, dropping the cost of the massive system prompt by up to 90%.

    Step 5: The Validation Bypass
    If the AI makes a mistake and the Validator Node sends back an error, the system deliberately skips Layer 1. It knows the previous output was flawed, so it must not return the cached mistake. It goes straight to Layer 2, appending the error feedback to the very bottom of the prompt. The AI still uses its "memory" of the static rules, but generates a fresh fix based on the new feedback.

    Step 6: Saving for the Future
    Once the AI successfully generates a valid blueprint, the harness pairs that final output with the original fingerprint from Step 1. It saves this pair into your Redis or local database. The next time you (or another parallel worker agent) request a blueprint for that exact Agent Card, the system will catch it at Step 2 and skip the AI entirely.
